01 · 문제

병목은 코드 작성이 아니라 검증과 지식입니다

지금은 고객사 업그레이드 요청이 오면 핵심 개발자가 그 고객의 소스를 직접 수정하고, 실제로 맞는지는 고객 팹 클린룸에 들어가서야 확인할 수 있습니다. 고객별 요구사항은 소스 곳곳과 핵심 개발자의 머릿속에 흩어져 있습니다.

이 상태에서 AI 코딩 도구만 도입하면 코드는 빨라지지만, 검증은 여전히 현장에서만 가능하고 무엇을 왜 바꿨는지는 여전히 추적되지 않습니다. 대표님이 1순위로 꼽으신 안정화와 부딪힙니다.

검사장비 기능 업그레이드 70%
호스트 연동 30%
검사 알고리즘, 검사 항목, 판정 기준, 화면·리포트 등 장비 자체 기능
기능이 바뀌면서 따라 바뀌는 SECS/GEM 보고 항목·이벤트

시사점. 호스트 연동 변경 30%는 검사 기능 변경 70%에 딸려 옵니다. 따라서 요구사항 하나를 바꾸면 검사와 호스트 연동이 함께 바뀌도록 요구사항(PRD)을 중심에 두는 구조가 맞고, 검증은 "바뀐 검사가 기존 이미지에서 같은 판정을 내리는가"부터 사무실에서 확인해야 합니다.

02 · 전체 구조

네 가지는 서로 다른 것입니다

논의에는 네 가지가 섞여 있습니다. 고객사에 설치되고 업그레이드되는 것은 ② 플랫폼 하나뿐입니다. ① PRD는 플랫폼의 설계도, ③ 시뮬레이터는 출고 전 검사, ④ 배포는 설치 절차입니다.

① PRD② 범용 플랫폼③ 가상 팹 시뮬레이터④ 배포 체계
정체고객별 요구사항과 합격 기준 문서장비 안에서 도는 소프트웨어 (제품)플랫폼을 시험하는 환경 (도구)설치·업그레이드·롤백 절차
위치인텍플러스 저장소고객사 장비 안인텍플러스 사무실·랩사무실에서 만들고 고객 팹에서 실행
업그레이드 때사람이 고치는 대상AI가 증분을 만드는 대상합격·불합격 판정합격본만 설치
고객에게 가는가변경 추적표 형태로 제출예보통 아니요 (망분리 고객만 반입형 키트)예
비유설계도건물준공 검사입주

왜 네 가지가 함께 있어야 하는가. PRD만 있으면 AI가 만든 증분을 믿을 근거가 없습니다. 시뮬레이터만 있으면 무엇을 시험해야 하는지가 흩어져 있습니다. 플랫폼 구조(코어 + 고객 설정 + HAL)가 없으면 증분을 고객마다 따로 만들어야 하고 시뮬레이터에 끼울 수도 없습니다. 셋이 맞물려야 ④ 배포가 빠르고 안전해집니다.

03 · ① PRD

업그레이드 대상은 소스가 아니라 PRD입니다

고객별 요구사항 가운데 자주 바뀌는 부분을 PRD 한 곳에 모으고, 업그레이드 요청이 오면 PRD를 고칩니다. AI는 PRD에서 바뀐 부분만큼만 기존 소스에 증분(변경분)을 만들어 적용합니다. 사람이 리뷰하는 대상이 코드에서 PRD로 바뀌고, 핵심 개발자의 일이 "코드 작성"에서 "PRD 확정과 승인"으로 옮겨 갑니다.

지금고객사 N곳 = 소스 N벌

요구사항은 소스와 개발자 기억 속에 흩어져 있습니다.

PRD 중심공통 PRD 1개 + 고객 PRD 차이분 N개

PRD의 구조가 플랫폼의 "공통 코어 + 고객 설정"과 같은 모양이 됩니다.

어디가 자주 바뀌는가: 반도체 검사 공정의 변경 지도

인텍플러스 장비가 놓인 후공정·미드엔드 검사 공정을 보면, 무엇이 자주 바뀌고 무엇이 거의 바뀌지 않는지는 산업 구조에서 이미 정해져 있습니다. 자주 바뀌는 쪽은 고객 공정과 제품의 사정에 따라 움직이고, 거의 바뀌지 않는 쪽은 물리 법칙, 광학, 기구, 표준 규격에 묶여 있습니다. 이 구분으로 PRD 범위를 정합니다.

D1

신제품·신규 패키지 도입

고객이 새 패키지를 양산에 올릴 때마다 검사 항목, 레시피, 검사 영역, 스티칭 범위, 지그가 바뀝니다. FC-BGA 대형화와 범프 피치 미세화, HBM·CoWoS 같은 2.5D/3D 패키지, SiP·이종 집적, 유리기판·패널 레벨 패키지가 계속 이 변화를 만듭니다.

D2

품질 기준과 불량 유형의 변화

고객의 최종 고객사가 품질 요구를 바꾸거나 새 불량 유형이 나타나면, 판정 기준·허용 오차·불량 분류 코드가 바뀝니다.

D3

수율 개선과 과검 줄이기

양산 중에는 양품을 불량으로 판정하는 과검을 줄여 달라는 요청이 끊이지 않습니다. 판정 임계값과 딥러닝 분류 모델이 계속 조정됩니다.

D4

고객 IT·MES 정책 변경

추적성 강화, 데이터 수집 확대, MES 교체에 따라 호스트 보고 항목, 결과·맵 데이터 형식, 2D ID 연동이 바뀝니다. 업그레이드의 30%인 호스트 연동 변경이 여기서 나옵니다.

D5

자동화·무인화

OHT·AGV·AMR 도입, 테이프 앤 릴과 라벨 작업 자동화에 따라 물류 인터페이스, 투입·배출 시퀀스, 라벨·바코드 양식이 바뀝니다.

고객 PRD · 고객 요청마다

고객별로 다르고 자주 바뀜

고객 대응 엔지니어가 초안을 쓰고 핵심 개발자가 확정합니다. AI가 증분을 자동 생성합니다. 플랫폼의 "고객 설정"이 됩니다.

제품 PRD · 신제품·옵션 개발 때

업계 공통으로 가끔 바뀜

제품 기획·개발팀이 씁니다. 사람이 주도하고 AI는 개발을 돕습니다. 플랫폼의 "제품 옵션 모듈"이 됩니다.

PRD 제외 · 거의 안 바뀜

물리·기구·표준에 묶임

설계 문서와 회귀 시험으로 관리합니다. AI 자동 수정을 금지하고 핵심 개발자가 직접 다룹니다. 플랫폼의 "공통 코어·HAL"이 됩니다.

두 가지 조건. 첫째, 세 영역 사이의 경계(인터페이스)를 명확히 정해야 합니다. 경계가 흐리면 고객 PRD의 변경이 코어로 번집니다. 둘째, PRD에서 뺀 영역도 시험에서는 빼지 않습니다. 코어의 현재 동작을 회귀 시험으로 남겨 두어야, 고객 PRD 증분이 코어를 깨뜨렸는지 잡아낼 수 있습니다.

확정 방법. 이 지도는 반도체 패키징 검사 산업의 구조에서 도출한 출발점입니다. 인텍플러스 핵심 개발자와 1~2회 워크숍을 열어 제품군별(후공정 iPIS, 미드엔드 iSIS, 모듈·SSD)로 확인하고 확정합니다. 운영하면서 고객 요청이 PRD 제외 영역에 반복해서 닿으면 그 영역을 고객 PRD나 제품 PRD로 옮깁니다.

PRD의 세 구성

본문

무엇을, 왜

요구사항 ID 단위로 변경 내용과 이유를 씁니다. 사람과 AI가 함께 읽습니다.

기계 판독 사양

설정·인터페이스

고객 설정 스키마, GEM 보고 항목·이벤트, 물류 시퀀스. AI와 플랫폼이 그대로 읽습니다.

합격 기준

시뮬레이터가 실행

골든 이미지와 기대 판정, 호스트 통신 시나리오, 택트 타임 한계. 문장만으로는 검사 기능을 정의할 수 없으므로 반드시 데이터로 붙입니다.

PRD 한 줄이 70%와 30%를 함께 만든다

PRD 변경 · REQ-A-INSP-042 범프 높이 측정 항목 추가, 허용 오차 ±3µm
  • 검사 엔진 증분측정 로직 추가70% 쪽
  • 고객 설정 증분판정 기준 ±3µm 등록설정만
  • 호스트 연동 증분GEM 보고 항목 추가 (자동으로 딸려 옴)30% 쪽
  • 시험 증분골든 이미지 판정 + GEM 시나리오 추가시뮬레이터

지금은 "검사를 바꿨으니 호스트 보고도 바꿔야 한다"를 사람이 기억해서 챙깁니다. PRD 방식에서는 한 번의 변경에서 자동으로 파생되고, 빠진 것은 시뮬레이터가 잡아냅니다.

PRD 작성 예시

prd/customer-A/REQ-A-INSP-042.yaml예시 형식 · 수치는 가상의 값
id: REQ-A-INSP-042
customer: 고객사 A            # 공통 PRD v3.2를 상속하고 차이분만 기술
type: 검사기능 변경
security_tier: B                # 보안 등급: AI에 넣을 수 있는 범위 결정
why: 신규 패키지에서 범프 높이 불량 유형 증가
what: 범프 높이 측정 항목 추가

spec:                            # 기계 판독 사양
  measure: bump_height
  tolerance_um: 3.0
  host_report:                     # 호스트 연동 30%: 검사 변경에서 파생
    svid: { id: 5120, name: BumpHeightMax, unit: um }
    attach_to_event: InspectionCompleted

acceptance:                      # 합격 기준 = 시뮬레이터가 실행
  golden_set: A-PKG-2026Q3         # 양품 / 불량 / 경계 사례 이미지셋
  regression: 기존 요구사항 판정 변경 0건
  new_detection_rate: ">= 99%"
  host_scenario: GEM-A-042.scn
  tact_time: 기존 대비 +2% 이내

trace:                           # 증분 생성 후 자동 기입
  code: []
  tests: []
  approved_by: ""

주의 ① PRD에서 소스 전체를 매번 새로 생성하면 안 됩니다. 같은 PRD를 넣어도 AI는 매번 조금씩 다른 코드를 만들고, 고객이 승인한 부분까지 흔들립니다. 소스는 계속 버전 관리하고, 바뀐 부분만 증분으로 만듭니다.

주의 ② 검사 기능은 문장으로 다 정의되지 않습니다. 경계 사례, 노이즈, 조명 조건의 판정은 골든 이미지와 기대 판정으로만 정할 수 있습니다. 합격 기준이 없는 PRD는 승인하지 않습니다.

04 · ② 범용 플랫폼

고객사에 설치되는 것: 코어 하나 + 고객별 설정

범용 플랫폼은 모든 고객사 장비에 같은 소스로 설치되는 장비 소프트웨어입니다. 고객사마다 다른 부분은 소스를 갈라서 만들지 않고, PRD의 기계 판독 사양에서 나온 설정과 플러그인으로 분리합니다.

고객사별 설정·플러그인CUSTOMER PROFILE

레시피·검사 항목, 판정 기준, 불량 분류, 호스트 보고 항목, 물류 시퀀스, 화면·리포트 양식. 고객 PRD에서 그대로 만들어지는 설정 파일입니다. 신규 검사 기능이나 핸들링 옵션처럼 제품 PRD로 개발하는 기능은 옵션 모듈(플러그인)로 둡니다.

공통 코어CORE

3D 측정 원리(WSI·광삼각법), 광학 캘리브레이션, 영상 획득·스티칭 엔진, 모션·핸들러 제어, SECS/GEM 통신 엔진, UI 골격. 변경 지도의 "PRD 제외" 영역으로, 모든 고객사에 똑같이 들어가고 거의 바뀌지 않습니다. 업그레이드의 70%인 검사 기능 변경은 대부분 코어가 아니라 위의 고객 설정에서 일어납니다.

HALHARDWARE ABSTRACTION

카메라, 조명, 모션, I/O를 표준 인터페이스 뒤로 숨깁니다. 고객 팹에서는 실제 장치에, 사무실에서는 시뮬레이터의 가상 장치에 연결됩니다. 플랫폼과 시뮬레이터가 만나는 지점입니다.

플랫폼의 업그레이드 단위

  • 패키지코어 버전 + 고객 설정 버전의 조합으로 배포합니다. 예: Core 3.2 + 고객A 설정 v14
  • 설정만호스트 보고 항목 추가처럼 설정만 바뀌는 PRD 변경은 코어를 건드리지 않고 설정 파일만 배포합니다.
  • 롤백이전 버전을 장비에 보관해 두고, 문제가 생기면 바로 되돌립니다.

06 · ③ 가상 팹 시뮬레이터

사무실에서 쓰는 것: PRD의 합격 기준을 실행하는 가상 팹

시뮬레이터는 고객사에 설치되지 않습니다. 인텍플러스 안에서, 고객사에 보낼 플랫폼 빌드가 PRD의 합격 기준을 통과하는지 판정하는 데만 씁니다.

장비 소프트웨어가 고객 팹에서 만나는 것은 세 가지입니다. 카메라와 센서로 들어오는 데이터, 모션·핸들러·I/O 같은 하드웨어, 호스트·MES·물류·앞뒤 설비 같은 상대 시스템입니다. 시뮬레이터는 이 셋을 소프트웨어로 대신합니다. 고객사 A에 나갈 빌드를 그대로 띄우고 주변을 가상 장치로 둘러싸면, 장비 소프트웨어는 자신이 고객 팹에 있다고 여기고 동작합니다.

전제 조건. 장비 소프트웨어가 카메라 SDK, 모션 보드, I/O 카드를 코드 곳곳에서 직접 부르고 있다면, 먼저 이 호출을 한 곳으로 모으는 HAL 작업이 필요합니다. 하드웨어 호출부는 고객별 소스 간 차이가 작은 경우가 많아 AI로 일괄 적용하기 좋은 영역이지만, 실제 난이도는 소스 진단 후에 판단해야 합니다.

한 번에 다 만들지 않고 4단계로 키웁니다

L1 · SIL

소프트웨어만으로 돌리는 시뮬레이터

PC 한 대에서 플랫폼 빌드와 가상 장치, 가상 호스트를 함께 띄웁니다. 시퀀스, 화면, 통신, 예외 처리를 검증합니다. AI 에이전트가 하루에도 수십 번 돌리는 기본 환경입니다.

L2 · 재생

골든 이미지 재생 회귀 테스트

고객별 대표 이미지셋(양품·불량·경계 사례)을 새 버전에 다시 넣고, 기존 버전과 판정이 한 건이라도 달라지면 표시합니다. 업그레이드의 70%를 직접 지키는 단계로, 가장 먼저 만듭니다.

L3 · HIL

랩 실장비 + 가상 팹

랩의 실제 광학 헤드나 핸들러를 연결하고 주변만 가상으로 둡니다. 택트 타임과 실제 조명·촬영 조건까지 출장 전에 확인합니다.

L4 · 트윈

고객 라인 단위 디지털 트윈

여러 장비와 물류 흐름을 묶어 라인 처리량과 무인화 시나리오를 검토합니다. 필요성이 확인된 고객에 한해 나중에 검토합니다.

시뮬레이터의 활용

검사기능 70%

판정이 바뀌지 않았음을 증명

새 검사 알고리즘을 골든 이미지셋 전체에 다시 돌려 과검·미검 증감과 택트 타임 변화를 숫자로 보여 줍니다. 의도한 변화와 의도하지 않은 변화를 구분한 목록이 나옵니다.

호스트 연동 30%

PRD의 GEM 사양대로 통신하는지

PRD 기계 판독 사양의 보고 항목·이벤트로 시나리오를 만들고, 가상 호스트가 재생해 빠진 항목과 순서 오류를 찾습니다.

현재 상태 기록

고객별 소스의 동작을 사진 찍어 두기

각 고객 소스의 현재 동작을 기록해 "현재 상태 PRD"의 합격 기준으로 씁니다. 플랫폼으로 옮길 때 "전과 똑같다"는 증거가 됩니다.

지식 이전

핵심 개발자 의존도 낮추기

신규 엔지니어가 고객 PRD와 시뮬레이터로 장비를 익힙니다. PRD와 시험이 그 고객의 지식 문서가 됩니다.

07 · 업그레이드 흐름

업그레이드 한 건은 이렇게 바뀝니다

지금

  1. 핵심 개발자가 고객 소스를 직접 수정 사무실
  2. 간단한 단위 확인 사무실
  3. 클린룸 입실, 설치 고객 팹
  4. 실제 자재로 기능·호스트 연동 확인 고객 팹
  5. 문제 발견 시 현장 수정 반복 고객 팹
  6. 재방문 고객 팹

PRD + 플랫폼 + 시뮬레이터

  1. AI가 고객 요청을 읽어 PRD 변경안 작성, 핵심 개발자가 확정 사무실
  2. AI가 PRD 변경분에서 코드·설정·시험 증분 생성 사무실
  3. 시뮬레이터가 새 합격 기준 + 기존 요구사항 전체 회귀 시험 사무실
  4. 요구사항 ↔ 코드 ↔ 시험 추적표 자동 생성, 핵심 개발자 승인 사무실
  5. 검증된 패키지 설치, 최종 확인만 수행 고객 팹

하네스 엔지니어링의 핵심. PRD가 "무엇이 맞는지"를 정하고, 시뮬레이터가 "맞는지"를 판정하므로, AI 에이전트는 사람 없이 "증분 생성 → 시험 → 재생성"을 반복할 수 있습니다. 사람은 처음(PRD 확정)과 끝(승인)에만 들어갑니다. 4단계의 추적표는 그대로 고객 변경 승인 자료가 됩니다.

08 · ④ 배포와 기존 장비 전환

이미 설치된 장비는 한꺼번에 바꾸지 않습니다

목표는 모든 고객 장비를 범용 플랫폼으로 옮기는 것이지만, 생산 중인 장비를 일괄 교체하면 고객 재승인, 클린룸 작업 집중, 위험 집중이 한꺼번에 일어납니다. 안정화가 1순위이므로 업그레이드 요청이 들어올 때마다 조금씩 옮깁니다.

방식내용평가
A. 일괄 교체설치된 장비 전부를 플랫폼으로 교체비권장. 위험·비용·고객 저항이 가장 큼
B. 신규 장비부터새로 출하하는 장비는 처음부터 플랫폼으로권장. 설치 기반이 더 갈라지지 않게 막음
C. 모듈 단위 공통화기존 고객 소스는 두고, 검사 엔진 → 통신 모듈 → HAL 순으로 공통 모듈로 교체권장. 업그레이드 70%가 검사 엔진이므로 효과가 가장 빠름
D. 업그레이드 시점 전환어차피 업그레이드하러 들어갈 때 그 고객 장비를 플랫폼 버전으로 교체권장. 추가 방문·추가 승인 부담이 가장 적음
E. 현행 유지업그레이드가 거의 없는 고객은 장비 수명까지 기존 소스로 유지선택. 현재 동작 기록과 PRD 역생성은 해 둠

전환할 때 고객이 묻는 질문에 대한 답

고객의 첫 질문은 "바꿔도 지금과 똑같이 동작하느냐"입니다.

  • 전환 전에 기존 고객 소스에서 AI가 "현재 상태 PRD"를 역으로 작성하고, 시뮬레이터로 현재 동작(판정 결과, 호스트 메시지)을 기록해 합격 기준으로 붙입니다.
  • 플랫폼 버전을 같은 조건으로 돌려 판정과 통신이 동일하다는 비교 리포트를 만듭니다.
  • 이 리포트를 고객 변경 승인 자료로 제출합니다.

어느 고객부터 전환하는가

기준먼저 전환할 고객
업그레이드 빈도요청이 잦은 고객 (효과가 가장 큼)
설치 대수장비가 많은 고객
보안 등급덜 엄격한 고객 (검증 데이터 확보가 쉬움)
소스 차이공통 코어와 차이가 작은 고객 (전환 비용이 낮음)
잔여 수명오래 쓸 장비 (곧 교체될 장비는 전환하지 않음)
09 · 보안

고객별 보안 등급에 맞춘 세 가지 운영 방식

고객 이미지와 로그, 그리고 고객 사양이 담긴 PRD는 반출이 어렵고, 그 정도는 고객마다 다릅니다. PRD마다 보안 등급을 적어 두고, 등급에 따라 AI에 넣을 수 있는 범위와 시뮬레이터 위치를 정합니다.

규칙내용지키는 방법

전체 재생성 금지AI는 증분만 만듭니다. 고객이 승인한 기존 코드는 유지합니다.증분 크기·범위 리뷰, 회귀 시험 전부 통과
현재 상태 PRD 역생성기존 고객 소스는 AI가 PRD 초안을 쓰고 핵심 개발자가 검토합니다.시뮬레이터 기록을 합격 기준으로 부착

11 · 추진

추진 순서

0 ~ 1개월

진단과 파일럿 고객 선정

보안 등급이 상대적으로 낮고 업그레이드가 잦은 고객 1곳을 고릅니다. 핵심 개발자 워크숍으로 변경 지도(고객 PRD·제품 PRD·PRD 제외)를 제품군별로 확정하고, 그 고객 소스의 하드웨어 호출 구조를 진단합니다. PRD 템플릿과 골든 이미지셋 확보 범위도 정합니다.

1 ~ 3개월

현재 상태 PRD + L2 골든 이미지 재생

파일럿 고객 소스 중 고객 PRD 영역에 한해 AI로 "현재 상태 PRD"를 역생성하고, PRD 제외 영역은 현재 동작만 기록합니다. 동시에 검사 엔진만 떼어 이미지 재생 회귀 시험을 만듭니다. 70%인 검사 기능 업그레이드를 바로 지킬 수 있어 효과가 가장 빨리 보입니다.

3 ~ 6개월

PRD → 증분 → 시뮬레이터 흐름 가동

HAL과 가상 호스트(SECS/GEM)를 붙여 L1 시뮬레이터를 완성하고, 실제 업그레이드 요청 2~3건을 PRD 방식으로 처리해 현장 체류 시간과 결함을 비교합니다. 신규 출하 장비는 이 시점부터 플랫폼 구조로 출하를 검토합니다.

6 ~ 12개월

고객 확대, 모듈 공통화, Tier C 키트

주요 고객으로 PRD와 시뮬레이터를 넓히고, 검사 엔진부터 공통 모듈로 교체합니다. 망분리 고객용 반입형 키트와 L3 랩 환경을 만듭니다.

기간은 소스 상태를 보지 않은 추정치입니다. 0단계 진단 결과에 따라 크게 달라질 수 있습니다.

12 · 한계

이 구조가 해결하지 못하는 것

  • 현장 방문이 없어지지는 않습니다. 고객사의 변경관리와 최종 검증 절차는 고객이 정합니다. 목표는 현장 작업을 설치와 최종 확인으로 줄이는 것입니다.
  • 광학·조명 조건은 완전히 재현되지 않습니다. 렌즈 오염, 진동, 조명 열화는 이미지 재생으로 재현하기 어렵습니다. L3 랩 검증과 현장 확인이 계속 필요합니다.
  • PRD와 골든 데이터의 품질이 전체의 품질입니다. 합격 기준이 허술하면 AI 증분도, 시뮬레이터 판정도 그만큼 허술해집니다.
  • 초기 작업과 규율이 가장 어렵습니다. 기존 고객 소스의 현재 상태 PRD를 만드는 작업(고객 PRD 영역으로 한정해 부담을 줄임), 고객 PRD·제품 PRD·코어 사이의 경계 설정, HAL 도입, 그리고 "소스 직접 수정 금지" 규칙을 현장에서 지키는 것이 성패를 가릅니다.
인텍플러스 공개 정보(홈페이지, 2026-10-09 확인): 1995년 설립, 고객사 300곳 이상, 출하 장비 3,300대 이상, 특허 231건 이상. 업그레이드 유형 비율(7:3), 고객별 소스 구조, 보안 조건은 대표 면담 내용 기준입니다. 제품군(iPIS·iSIS·모듈/SSD)과 검사 항목은 인텍플러스 제품 페이지, CoWoS·유리기판 대응은 2026년 언론 보도를 참고했습니다. 변경 지도는 산업 구조에서 도출한 가설로, 인텍플러스 내부 확인이 필요합니다. PRD 예시의 수치와 그 밖의 기간·효과는 제안 단계의 가정과 추정입니다.
